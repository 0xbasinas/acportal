## Host enforcement

The local client and network host use trusted operator registry files and explicitly configured workspace roots. Canonical paths prevent lexical traversal and resolve existing symlinks before root checks. A process cwd outside those roots is rejected. Process arguments are passed as an array; no shell interpolation is used.

Registry configuration can set environment values and commands, so write access to the registry is equivalent to permission to run an executable. Protect host config files with OS permissions. The registry is not editable by an unauthenticated remote caller.

Permission callbacks wait for explicit choice. Supplied option IDs are validated, duplicate answers fail, and cancellation responds with a cancelled outcome. The only host-level automatic decision is the opt-in, per-agent shell-line auto-review described below; it is off by default and never applies to file writes or plain program terminals. (A write of text a file already holds is answered without a prompt because it changes nothing; see below.) Goose's registry sets approval mode; agents remain responsible for correctly requesting consent for their own operations.

The host implements workspace-scoped ACP text reads and writes. A directory handle is opened for the selected workspace; actual file operations stay relative to that capability. Reads validate the attached ACP session ID, file type, UTF-8 and size. Unix file opens use nonblocking flags to avoid hanging on named pipes, and filesystem workers are bounded globally. Every write that would change a file requires an explicit host permission decision for its proposed diff (a write of text the file already holds is answered without one; see below). Denial and cancellation return an error to the original callback. The host checks the approved content snapshot before an atomic replacement, rejects leaf symlinks and preserves existing Windows DACLs. These checks do not provide an atomic compare-and-swap against concurrent external writers. On Unix the replacement keeps the existing file's owner, group and mode bits; when the host user may not give the new file the same owner and group (for example a file owned by another user that is only group- or world-writable, or a group the host user is not in), the write is refused and the file is left unchanged instead of being taken over. New files are created owner-only (0600). Extended attributes and POSIX ACLs are not copied. A hard link inside the workspace to an outside file can still be read; a write replaces only the workspace link.

Host consents cover only what an agent asks the host to do through ACP callbacks (`fs/write_text_file`, `terminal/create`). An agent that reads, edits or runs commands with its own built-in tools does that in its own process, as the host user, without any host check: workspace containment, write consent and terminal consent do not apply. OpenCode 1.18.35 is such an agent: by default it edits files and runs shell commands with no permission request at all; with `"permission": {"edit": "ask", "bash": "ask", "external_directory": "ask"}` in its own configuration it asks first, but it writes the file itself at about the same time as it sends the host `fs/write_text_file`, so refusing the host write consent does not stop the edit, and an `external_directory` approval let it read `/etc/hostname` outside the workspace (see [real-agent testing](real-agent-testing.md#opencode-session-workflow-8-october-2026-linux-about-2315-athens)). For such agents the agent's own permission request (forwarded to the phone as an ordinary agent permission) is the effective gate; refusing it kept the file unchanged. Two host-side aids exist. If a refused or cancelled host write is found already applied (the file now holds exactly the proposed text), the host marks the failed tool call with `_meta.acpdWrite: "changed-without-consent"` and a notice. If a write asks for text the file already contains, there is nothing to consent to: the host answers success without asking or writing and shows a completed "already up to date" tool call (`_meta.acpdWrite: "unchanged"`). Both are best effort (a later agent write is not seen). They report; they do not contain anything. Use an OS sandbox or a dedicated account for real containment. The operator can mark such an agent with `"ownTools": true` in the registry; the flag reaches discovery and session metadata, and the Android app then shows "Uses its own tools" and a warning that those actions skip the host's approval prompts and workspace access settings. The host cannot detect own-tool use itself, so an unmarked agent shows no warning; the wording claims only what the host cannot see. With OpenCode's own "Always allow" for edits, later edits produced no prompt and no host callback at all (see [real-agent testing](real-agent-testing.md)).

Form elicitation is off unless the phone opts in per session. It is form mode only (no URL mode, so the host never asks a phone to open an agent-supplied link), limited to the attached session, bounded with the pending permissions, and answers are checked against the requested schema before the agent receives them. The phone user types the answers, so an agent can still ask for anything; the sheet tells users not to enter passwords or keys.

Terminal callbacks require the attached session and a session-owned handle. Creation resolves the executable and requires explicit host consent before launching it with literal arguments. Output, handle count, live process count and runtime are bounded. Cancellation, release and shutdown stop ordinary descendants through the same cleanup guard as agents. Writes and terminal creation during initial session setup are rejected because a controller cannot yet review consent. These restrictions are not an OS sandbox: trusted agents and approved commands run with the operator's privileges. A dedicated service account and OS sandboxing are needed for stronger containment.

## Workspace scope of shell commands

Three layers keep host-run commands to the session workspace. All are agent-agnostic.

1. **Working directory.** `terminal/create` must name a cwd inside the workspace; it is canonicalized before consent and checked again just before the process starts.
2. **Scope check (always on).** Every host terminal consent carries `_meta.acpdScope {outsideWorkspace: [...], sandboxed}`. The host lists absolute, `~`, `$HOME` and `..` operands (also `--flag=/path`), redirect targets and `cd` targets that resolve outside the workspace, lexically and through symlinks; relative operands after a `cd` out of the workspace also count, and a line that cannot be parsed is listed as `(unparsed command)`. A non-empty list forces a person to decide: auto-review rules cannot allow it and it is never sent to the model reviewer. The same check annotates an agent's own `session/request_permission` when its `rawInput` carries `command`, `cmd`, `shellLine` or `script` (with `agentTool: true`); there it is a warning only, because the host does not run those tools. The desktop approval card shows a red "Outside the workspace" box with the paths, and desktop notifications never offer "Approve once" for such requests.
3. **OS sandbox (per agent, default on where supported).** See `sandbox` in [agents](agents.md). With bubblewrap, a command that names `/etc/passwd` can still read world-readable system files, but it cannot write outside the workspace or see the home directory. On Windows the same setting uses an AppContainer (the approach of Chromium and Codex CLI): acpd starts itself as a small launcher (`acpd __acpd-sandbox-exec`) that creates a AppContainer profile for the workspace (`acpd.sbx.ws.<hash of the folder>`, one per workspace), adds an inherited ACL entry for its SID on the workspace unless it is already there, and runs the approved command line unchanged inside the container with only the `internetClient` and `privateNetworkClientServer` capabilities, in a kill-on-close job. Windows writes an inherited entry onto every existing file below the folder, which takes tens of seconds in a repository with build output, so the grant is made once per workspace (in the background when a sandboxed session opens) and kept for later commands; the host removes the entries and profiles when it stops. Commands in one workspace therefore share one container identity; isolation from the rest of the disk is the same. A host that crashes leaves the entry behind; the next host uses the same profile for the same folder and removes it when it stops (the entry names an `S-1-15-2-…` SID, and `icacls <workspace> /remove *S-1-15-2-…` also clears it). Files readable by ALL APPLICATION PACKAGES (most of `C:\Windows` and `C:\Program Files`) stay readable. A restricted token with low integrity was not used as a fallback because it does not stop reads of the user profile; where AppContainers are unavailable, the card says "Not sandboxed". Only the `acpd` executable enables the launcher, so programs embedding the library run terminals unsandboxed. Granting the ACL walks the whole workspace once per command, which is slow on very large trees.

   **Windows shells.** Shell lines run in `cmd.exe` by default; `[windows] shell = "pwsh"` or `"bash"` in `config.toml` (or an agent's `shell`) selects PowerShell or Git Bash (see [agents](agents.md#windows-shell)). Git Bash is MSYS2-based and cannot start inside the sandbox: MSYS2 creates named objects and a signal pipe at start-up that the sandbox's token may not create (`couldn't create signal pipe, Win32 error 5`; the same failure is reported for other Windows sandboxes in [openai/codex#7031](https://github.com/openai/codex/issues/7031) and [deepseek-harness#1613](https://github.com/deepseek-ai/deepseek-harness/discussions/1613)). acpd's Windows test `spike_git_bash_cannot_start_in_the_appcontainer_but_powershell_can` checks this on the CI runner. So a sandboxed line asked to use Git Bash runs in PowerShell (or `cmd.exe` when PowerShell is missing) and the card says why; Git Bash runs only for agents with `sandbox: off`, unconfined. A sandboxed command that names an MSYS2/Cygwin program directly (for example `Git\usr\bin\grep.exe`) is refused before approval with an error naming the program; programs started from inside a line cannot be checked and will fail to start.

The scope check is heuristic: it cannot see paths built at run time (`$(...)`, variables other than `HOME`, scripts that open files themselves). The sandbox is the enforcement layer; where it is unavailable, read every command.

## Shell-line auto-review (opt-in)

Off by default. Without a `[shell_review.<agent-id>]` table that sets `rules = true`, every shell line waits for an explicit phone decision, as described above. When enabled for an agent, each shell line is first classified by a deterministic rules layer and, optionally, by a model reviewer. Plain program terminals (`host-terminal`) are never auto-reviewed.

```toml
[shell_review.goose]
rules = true

[shell_review.goose.model]          # optional
base_url = "https://api.deepseek.com"
model = "deepseek-flash"
api_key_env = "DEEPSEEK_API_KEY"    # env var name only; the key is read from acpd's environment
timeout_seconds = 10
max_requests_per_minute = 6         # per session
max_command_bytes = 2048
```

**Rules layer** (`acpd/src/shell_review.rs`). The line is tokenized by a POSIX `sh` lexer (single/double quotes, backslashes, `$(...)`/backticks kept as one word, operators `&& || ; | &`, `( )`, redirections with io-numbers). No expansion is performed; expansions are only detected.

- *Hard deny* (refused, the agent gets `-32602` "Shell line refused by acpd auto-review (rules): <reason>"): `sudo`/`su`/`doas`/`pkexec`/`run0`; `shutdown`/`reboot`/`halt`/`poweroff`/`init`, `mkfs*`; recursive `rm` of `/`, `~`, `$HOME`, `.`, `..`, `../*`, a `…/..` path or a top-level system directory, or with `--no-preserve-root`; `dd of=/dev/…`; redirects into raw disk devices; anything piped into a shell (`… | sh`), and download tools piped into an interpreter (`curl … | python3`).
- *Auto-allow* only when every command is on a small allowlist and they are joined only by `&&` or `;`: `ls`, `pwd`, `cat`/`head`/`tail` on paths inside the workspace, `git status|diff|log` (no options before the subcommand, no `--output`/`--ext-diff`), `python[3] -m unittest|pytest`, `pytest`, `cargo test|check`, `npm test`, and `cd` into a directory inside the workspace (later paths are checked from there). `2>&1`, `>&2` and `>/dev/null` are allowed; every other redirect is not.
- *Ask the phone* for everything else. Lines with file redirects, pipes into shells, substitution or variables, `eval`/`exec`/`source`, backgrounding, subshells, multiple lines, comments, environment assignments, `~`, paths outside the workspace (lexically or through symlinks), deletion/write/network/process tools (`rm`, `mv`, `cp`, `tee`, `sed`, `curl`, `wget`, `ssh`, `nc`, `kill`, `xargs`, `env`, …), or repository/package changes (`git push/fetch/clone/config/reset/clean/checkout`, `npm/pip install`, `find -exec/-delete`) are marked *sensitive*: the model may deny them or leave them to the phone, but can never allow them. Filename patterns require manual consent because expansion can select paths outside the workspace, including through symlinks. Unknown programs, pipes between programs and `||` are *undecided* and may be allowed by the model. Agent-supplied terminal environment overrides also require manual consent and bypass model review; PATH and loader variables can change what an otherwise allowlisted line executes. Environment values remain excluded from consent metadata and reviewer payloads.
- *Inert environment overrides* (every agent with `rules = true`; per-agent opt-out `inert_env = false`). Any other agent-supplied terminal environment override forces the phone and bars the model from allowing the line. A request whose overrides (at most 16) are all on this agent-agnostic allowlist is reviewed as if it had none (`inert_variable` in `shell_review.rs`):

  | Name | Allowed values | Why inert |
  | --- | --- | --- |
  | `PAGER`, `GIT_PAGER` | `cat` or empty | the no-op pager; any other value names a program to run, so it asks |
  | `TERM` | 1-32 of `[A-Za-z0-9-]` | selects a terminfo entry for output formatting; no paths |
  | `NO_COLOR`, `CLICOLOR`, `CLICOLOR_FORCE`, `CI` | empty, `0`, `1`, `true`, `false` | colour/non-interactive flags |
  | `FORCE_COLOR` | empty, `0`-`3`, `true`, `false` | colour level |
  | `COLUMNS`, `LINES` | 1-4 digits | terminal size for formatting |
  | `LANG`, `LC_ALL`, `LC_CTYPE`, `LC_MESSAGES`, `LC_NUMERIC`, `LC_TIME`, `LC_COLLATE`, `LC_MONETARY` | `C`, `POSIX`, or `ll[_CC][.codeset][@modifier]` (letters/digits only, never a path) | language and formatting of messages; `LOCPATH` is not allowed |
  | `AGENT_SESSION_ID` | exactly the request's ACP `sessionId` (already checked to be this session), 1-128 of `[A-Za-z0-9_.-]` | an agent marker naming its own session; read by no shell, interpreter, loader or git. Goose 1.53.0 sends exactly this (captured 11 October 2026) |

  Never allowed, whatever the value: `PATH`, `LD_*`, `DYLD_*`, `*_OPTIONS`, `PYTHON*`, `NODE_*`, `BASH_ENV`, `ENV`, `SHELL`, `IFS`, `PS4`, `PROMPT_COMMAND`, `GIT_*` other than `GIT_PAGER`, `LOCPATH` and every name not in the table. One unknown or extra entry, a different value or a different case keeps today's behaviour. The line itself still goes through the rules: filename patterns, redirects and so on still ask the phone, hard-deny is unchanged, and the model still cannot allow rules-sensitive lines. The default is on because review itself is already per-agent opt-in (`rules = true`), the list only admits presentation settings and the agent's own session id, and without it agents that always send such a marker (Goose) could never auto-approve anything.
- On Windows the rules do not parse `cmd.exe` syntax; every line is undecided-sensitive and goes to the phone (or is denied by the model).

**Model layer** (optional). For lines the rules did not decide, acpd POSTs to `<base_url>/chat/completions` with `temperature 0`, `max_tokens 200`, `response_format: json_object`, a fixed system prompt (`MODEL_SYSTEM_PROMPT` in `shell_review.rs`) and one user message containing only `{"agent","cwd" (relative to the workspace),"shell","command"}`. File contents, env values and conversation text are never sent. The reply must be exactly `{"decision":"allow|ask|deny","reason":"…"}` in `choices[0].message.content`. Any transport error, non-2xx status, timeout, reply over 64 KiB, malformed or fenced JSON, unknown decision, missing key env var, rate limit hit, line over `max_command_bytes` or more than four reviews in flight means *ask the phone*. A model `allow` of a sensitive line becomes *ask*. The rules layer runs first, so a hard-denied line never reaches the model. Redirects are disabled on the HTTP client; `base_url` must be HTTPS (plain HTTP only for loopback, used by tests) and must not embed credentials. Retired DeepSeek models (`deepseek-chat`, `deepseek-reasoner`, `deepseek-v4-flash`) are rejected for `deepseek.com` URLs.

**Visibility.** Every automatic outcome is published to the session as a host tool call with `_meta.acpdAutoReview {decision, layer, reason}` and the exact `rawInput.shellLine`: `allow` starts the terminal (output streams as usual and the phone can stop it with cancel), `deny` shows a failed tool call, `reviewing` marks a line waiting for the model, and a line that still needs the phone carries the same object in the consent's `_meta`. The host log records only `shell line auto-review decision=<allow|ask|deny> layer=<rules|model>`, never the line, cwd or reason. A cancel while the model is reviewing answers the agent with `-32800` and nothing runs.

**Honest limits.**

- An allowlist is not a sandbox. `python -m unittest`, `pytest`, `cargo test` and `npm test` run project code; anyone who can edit the workspace (including the agent, through approved writes) can make "run the tests" do anything the host user can. `git status/diff/log` honour repository config (pagers, `core.fsmonitor`, diff drivers), which an untrusted repository controls. `cat`/`head`/`tail` of a workspace file can print secrets stored there to the agent.
- Program names are resolved through acpd's `PATH`; a writable directory early on `PATH` can shadow `ls` or `git`.
- Path checks are lexical plus a symlink check at review time; a file swapped for a symlink between review and execution is not caught.
- The model is advisory and can be wrong or manipulated by text inside the command; that is why it can only allow lines the rules already consider low-risk and why any doubt goes to the phone. The command line itself (which might contain a secret the agent typed) is sent to the configured provider.
- Provider keys placed in acpd's environment (for Goose or for the reviewer) are inherited by the agent and therefore by commands it runs; prefer the agent's own credential store.
- Rate and size limits are per session. Tests cover the rules table, lexing of tricky quoting, config defaults/validation, and the model layer against a local mock server (allow, deny, malformed, timeout, sensitive-allow downgrade, cancel while reviewing).

Frames, pending requests, permission requests, history bytes, history event count, admitted caller input bytes and active sessions are bounded. Live subscribers cannot extend the lifetime of evicted history. A deadline closes ambiguous stalled connections. On shutdown, crash or timeout the host terminates the agent's cleanup job on Windows or its process group on Unix, then reaps the direct child. The Windows job handle is non-inheritable and kills assigned members when closed. Windows processes start suspended and run only after assignment to the job, so they cannot create children outside it first; a failed assignment or resume kills the process. Unix processes that deliberately leave the group also escape group cleanup, and an abrupt daemon kill cannot run Unix cleanup. This is not an OS sandbox. Windows tests verify two descendant generations stop on explicit removal, agent crash and timeout. Linux and macOS Actions tests verify the same for agents, and terminal descendants after kill, release and service drop. This covers ordinary process-group cleanup, not deliberate group escape or cleanup after abrupt Unix daemon termination.

The host logs session UUID lifecycle events, not prompts, code, command arguments, env values, authorization headers or agent stderr. The optional `[logging]` file sink stores those same records in an owner-only file with size rotation and a fixed number of retained files, so its disk use is bounded. The optional `frame_metadata` mode logs only fixed-vocabulary frame metadata (direction, kind, sanitized method/update name, error code, size), never params, results, error text or ids. `doctor --agent` prints only advertised sign-in method ids/names and JSON-RPC error codes. Doctor reads the configured TLS private key only to confirm it matches the certificate and never prints key material or file paths in TLS failures. Stderr is drained in fixed chunks to avoid deadlock. Raw agent error text is replaced by its JSON-RPC error code. The local UI still renders agent content by user request; terminal output and local cache must be treated as sensitive.

## Per-session manual approval ("Ask for everything")

Auto-approve (`[auto_approve.<agent>]`) and shell review (`[shell_review.<agent>]`) are host configuration. Before this switch they applied to every qualifying session of that agent, and a person starting a session could not opt out. `workspaceAccess.manualApproval` (boolean, default false, omitted when false) is that opt-out, for one session.

**What changes.** When it is true at session start, the host does not start the auto-approve watcher for the session (`auto_approve::spawn` returns first) and does not hand the agent's connection a shell reviewer (`session.rs`, the `shell_review` argument is `None`). So every permission request and every shell line goes to the person, as it does for an agent with no configuration at all. The flag is part of the stored session metadata and is shown back in `workspaceAccess`.

**Why it is safe to add.** It can only remove help the host would give. It cannot allow anything, widen a right, change `workspace_roots`, or skip a consent that is mandatory today: reads, writes and terminals still need the same `readFiles`, `writeFiles` and `terminal` flags and the same host-side consent. The hard-deny list, the OS sandbox, workspace containment and the scope check on terminal consents are unaffected, because they are not approvers. Any client that can create a session can already create it with fewer rights, so choosing "ask more" adds no authority. The flag is part of `WorkspaceAccess`, which is `deny_unknown_fields`, so an older host rejects a request that carries it instead of silently ignoring it and answering for the person.

**What it does not cover.**

- An agent with `ownTools` runs its own edits and commands without asking the host. Manual approval cannot stop that, and the presets text says so.
- A delegated task (orchestrator) inherits the switch from the session that delegated it: the host reads the parent's `manualApproval` when it opens the child, and a parent it cannot read counts as manual. So `[auto_approve]` and shell review stay off for the whole tree. A supervising agent (`/v1/sessions/{id}/supervisor`) is a different, explicit opt-in that hands requests to another agent; it is not switched off by this flag.
- A session loaded after a host restart is a new session, and the host does not remember the choice on the person's behalf. The clients send it again: Android passes the stored session's `manualApproval` when it resumes, and the desktop passes the composer's current access when it opens an earlier session.
- Remote (`ws`) agents never had these approvers, so the switch changes nothing for them. It is not offered for them.

**How it is offered.** `GET /v1/presets` lists `ask-all` ("Ask for everything") only when the host would otherwise answer something itself: auto-approve is on and writes are allowed, or shell review is on and commands are allowed. With neither configured, `supervised` already means the same. The preset names only flags the client can already send (`readFiles`, `writeFiles`, `terminal`, `manualApproval`); `POST /v1/sessions` still rejects a `preset` field. The desktop shows the active setting, and keeps showing that the host's rules are off if the person then changes a single right ("Custom").

**Tests.** `acpd/tests/auto_approve.rs` runs the same agent, policy and request twice: the host answers it by itself without the switch and leaves it to the person with the switch; removing the guard made that test fail. `acpd/tests/lifecycle.rs` has the matching Linux-only shell test. `acpd/src/presets.rs` and the desktop tests cover when the preset is offered and that only it sets the flag.

## Per-session "Auto-approve everything"

`workspaceAccess.yolo` (boolean, default false, omitted when false) asks the host to answer the session's permission requests and shell lines itself, so a person is not asked about each edit and command. Unlike `manualApproval` it **allows** things, so the host refuses it unless the operator turned it on for that agent:

```toml
[yolo.goose]
enabled = true
```

Without that table, or for an agent on another host, `POST /v1/sessions` with `yolo` fails ("not turned on for this agent"), and so does combining it with `manualApproval`. A paired device therefore cannot grant itself this on its own, and a delegated task never inherits it (a child starts without it).

**What it answers.** The auto-approve watcher runs for the session with the highest ceiling (never readable from configuration): the agent's own permission requests and the host's file-write consents are answered allow-once, whatever their risk. Shell lines and terminals use the built-in rules reviewer, with no model: a line the rules would only ask about is allowed, and each answer is marked on the tool card as an automatic review ("auto-approve everything").

**What still stops.**

- Credential and settings paths, and anything the deny rules refuse, are left to the person. A request that names a path outside the session folder is left to the person too.
- A line on the hard-deny list (sudo/su, power and mkfs, recursive delete of root, home or system paths, raw device writes, pipes into shells) is refused. On Windows the shells are not parsed, so a short best-effort list (recursive delete of a drive or user folder, diskpart, format, bcdedit, registry-key deletion, shutdown, user accounts) stands in; the AppContainer sandbox is the real boundary there.
- A line that names a path outside the folder, or carries environment overrides, still asks.
- Forms and every other question that needs a person's input still ask.
- The OS sandbox, workspace containment and the scope check on terminal consents are unchanged. An agent that edits with its own tools (`ownTools`) is still answered by the agent, not the host, and its requests stay with the person.

**How it is offered.** `GET /v1/presets` lists `yolo` ("Auto-approve everything") only when `[yolo.<agent>]` is enabled, the agent is local and writes or commands are allowed. The desktop never remembers it: every session has to choose it again. After it, check the result in Git.

**Tests.** `acpd/tests/yolo.rs` (answers execute/delete/fetch; still leaves `.env` and `../outside.txt`; an ordinary session on the same host is still asked; refused when not allowed or combined with manual approval); `acpd/tests/lifecycle.rs` (Linux: an asked line runs, `rm -rf /` is refused, a path outside the folder asks); unit tests in `shell_review.rs`, `presets.rs` and `config.rs`. Removing the outside-path guard made the `../outside.txt` case fail.

## The desktop app's in-app browser

The desktop app can show a page next to a conversation. This is a boundary of its own: the page is untrusted and must not reach the app, the host token or the person's other sites.

- **Isolation.** The page runs in a separate Chromium view and session with no preload, no Node, no access to the app's IPC and `sandbox`, `contextIsolation` and `webSecurity` on. The app's own window keeps its existing rules (no navigation, `https:` links only to the system browser).
- **Where it may go.** Loopback addresses (`localhost`, `*.localhost`, `127.0.0.0/8`, `::1`) and the sites the person added. Typed addresses, links, `window.open` and redirects all go through one check (`electron/browserRules.ts`); anything else opens in the person's own browser or is refused, and only `http:`/`https:` ever leave through the system browser. Addresses with a user name or password, `file:`, `javascript:`, `data:` and browser-internal schemes are refused.
- **Permissions.** Every permission request and check is refused; downloads are cancelled unless the person turned them on; certificate errors are not overridden.
- **State.** The session is in memory and starts clean every launch unless the person turns on *Remember sign-ins*, which uses a separate persistent profile.
- **Sending a page to an agent.** A screenshot, the selected text or the address is attached to the person's next message only when they choose it from the menu, and is sent only when they send the message. An agent cannot read or drive the browser. The page's selected text is untrusted content like any other message attachment.
- **What it does not cover.** A page on localhost is as trusted as the dev server behind it: it can call other sites like any web page, and it can read files only through that dev server.

Tests: `desktop/test/browserRules.test.tsx` (the rules, including look-alike hosts and unsafe schemes) and `desktop/test/browser.test.tsx` (the panel and the message box). The isolation itself was checked in the running app: the page has no `window.api`, `require` or `process`, and camera, location and notification requests are denied.

## Implemented network security

Bind to loopback by default. Remote listeners require TLS through a verified reverse proxy or a built-in TLS listener. Android rejects cleartext remote WebSocket URLs and certificate validation failures. Never install a permissive trust manager.

`acpd pair` generates a random, one-use code through the operator-only local state directory. Code exchange issues a device-specific 256-bit bearer credential. The host stores only its SHA-256 digest; credentials expire and can be revoked. Codes expire after 60 seconds, are consumed atomically under an interprocess file lock, and are blocked after five failed attempts. Rate limiting is global; per-source limits remain future hardening. State is protected by owner-only permissions on Unix and an owner/System DACL on Windows. Tokens never appear in discovery, diagnostic or device-list responses.

Separate operator endpoints from paired-device endpoints. Device credentials authorize discovery and sessions only within the configured workspace roots. Authenticate before any discovery, replay or WebSocket upgrade. Bound input before deserialization and reject session ID mismatches. A single-controller lease prevents two clients from responding to the same permission simultaneously.

Android encrypts credential blobs with Keystore-held AES-GCM keys and unique nonces. Room stores aliases only. Optional biometric protection needs an explicit locked state and reconnect behavior. Backups must exclude private material and cached code unless opted in.

Per-connection MCP definitions also use the no-backup encrypted vault, with aliases in DataStore. This includes URLs, arguments, environment variables and headers, since any of them may carry credentials. Editing drafts containing these values are not placed in saved instance state. MCP definitions are intentionally supplied to the chosen host's agent for new/load setup and retained in host process memory across authentication. The host does not add them to restart metadata or connection diagnostics. MCP executables and network endpoints are user-configured agent integrations, and are not contained by the host filesystem callback boundary.

Filesystem tests cover allowed line ranges, outside roots, invalid session IDs, directories, binary and oversized files, symlink escapes and reads during loading. Write tests cover creation/replacement, protected Windows DACLs, hard-link isolation, changed files, expired commits, approval, denial, cancellation, duplicate answers and reconnect recovery. Terminal tests cover explicit consent, duplicate answers, reconnect without duplicate execution, retained output after release, session-scoped handles, UTF-8 and byte limits, exit waiting, kill, cancellation and descendant cleanup on Windows. Shell-line tests cover detection (with and without separate args), consent shape and option ids, denial and cancel-while-pending (nothing runs), approval running the exact shown line, refusal when a plain-command option id is offered for a shell consent, and Linux cleanup of the shell plus a background grandchild on release.

## Release gate

Workspace access policies independently gate host-provided file reads, reviewed writes and all five terminal callbacks. Negotiation does not suffice: disabled callbacks are rejected even when the agent ignores capability flags. Policies survive metadata retention, while an explicit new/load operation may choose a different policy. This boundary applies only to host-provided services, not agent-owned tools or MCP integrations.

This increment is not a security-audited production service. Pairing, TLS configuration, authorization, protected credential/session metadata, process cleanup and Android secret storage are implemented. Session recovery never replays pending permissions or prompts. Unix process-cleanup verification, optional delivery-journal persistence, broader TLS deployment tests and resource stress testing remain release work.

## Folders and agents added from the phone

A paired device can list directory names anywhere on the host (`/v1/filesystem/directories`), add or remove workspace roots, and register or remove agent CLIs (`/v1/workspaces`, `/v1/agents`). This is deliberate: a paired phone already starts agents and approves writes on the host, so these routes grant no authority beyond a device token, but they do let that token widen which folders agents may use and which programs the host will launch. Revoke a device to remove that authority. Limits: directory listings return folder names only; adding needs an existing directory; the `--version` check and registration use the same literal-argument, no-shell launch rules as agents (the check also has a 5 second limit and reads at most 4 KiB); agents and roots from the host's own config or registry cannot be replaced or removed from the phone; everything the phone adds is stored in `<state_directory>/user-settings.json`, written atomically and owner-only on Unix, and a saved agent that no longer validates is skipped at startup rather than blocking the host. Existing sessions keep the launch settings they started with.

## Control handoff, shared drafts and the agent probe

- **Takeover** (`takeover=true` on connect, feature `controlTakeover`): any paired client app (phone or desktop) can take the controller lease from another client app. This gives it no authority it lacked, because either client could already control the session. The replaced client gets `control_taken` and keeps a read-only view. A lease held by a peer bridge is never taken over. Pending permission requests stay pending and are answered by whoever controls the session.
- **Shared drafts** (`/v1/shared`, feature `sharedDrafts`): drafts, titles and per-folder prompt history are stored in `<state>/shared.json`. The file is written atomically and owner-only on Unix, and its size is capped per item and in total. Paired client apps can read and write it; peers cannot. Prompts typed into a draft or kept in the history are stored on the host in plain text. Attachments and MCP/checks settings are not shared.
- **Agent probe** (`POST /v1/agents/{id}/probe`, feature `agentProbe`): this starts a registered agent in an approved folder, as creating a session does. The session has no file, terminal or MCP access and gets no prompt, and it is removed straight away. Only the reported `modes`/`models`/`configOptions` are kept, in memory.
